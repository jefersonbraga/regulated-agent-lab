# Threat model

Scope: the agent actions in this lab, from the signed-in user's message to the payment
(simulated, or the card processor in test mode, paid on its hosted page or by the agent from the
user's wallet). Assets: the payment (amount, single capture), the saved-card references and the
spending limit in the wallet, the single-use payment tokens, the audit trail, the console
sessions, and passenger personal data. No real money moves, and no card number ever enters the
lab (the processor vaults it).

**Residual risks (not covered here):** the injection guard is a regex tripwire, so new phrasings
get through (the design rule, not the regex, is the real defence). A token can be replayed within
its TTL because there is no nonce or `jti`. The payments server does not itself check the amount
against the approved quote, nor that the hold is still live; those checks happen in the gate (signed approval token) and on the
agent side. Code running in the same process could still read the signing secret or call the
MCP clients directly; identity binding closes the in-graph bypass, not a compromised process. Removing lines from the
*end* of the audit log, or emptying it, is detected through the `audit.jsonl.head` anchor
(last `seq` and `hash`), and `append` refuses to extend a log whose tail does not match it, so the
next ordinary write cannot launder the tampering. The exception is the trace of a crashed writer
(its line fsynced, the head not yet replaced): exactly one valid, correctly chained entry past an
intact head is adopted by the next append and audited as `head_recovered` (`from_seq`, `to_seq`).
The trade-off: someone who can write only `audit.jsonl` can get one forged, chained entry adopted,
but it stays visible next to a `head_recovered` event; two or more entries past the head are refused. But that anchor sits next to the log: someone who can write both files
can truncate the log and rewrite the anchor, or rewrite the whole file with fresh hashes. A real
deployment would publish the head to a separate store or sign it. The wallet shares one
processor test account with the payments institution (a real wallet would hand over a network or
shared payment token, not processor ids), the user's card and limit are managed by the API
process calling the wallet module in-process, and the mandate is per booking, not per period. API users are demo accounts
in an environment variable (no MFA, no identity provider), logout revokes a session only in the
process that served it, and the rate limits are per process. The webhook route runs in the agents' API process (it delegates
verification and storage to the payments module), so a compromised API process could read the
endpoint secret; effects of an event are applied at least once, and reconciliation runs on
demand, not on a schedule.

## Regulatory hook → control in this lab

> **Illustrative mapping, not a compliance claim.** It shows where a control would plug in. It
> is not evidence that this lab meets any regulation or standard.

| Regulatory hook | Control in this lab |
|---|---|
| EU AI Act: human oversight (Art. 14) | `approval` node: the graph stops at `interrupt()` before any payment, and the human sees the exact quote and hash |
| DORA: ICT incident management and traceability | Hash-chained audit log with `verify`, covering every tool call, denial, injection flag and decision |
| GDPR / Swiss FADP: data minimisation | `redact()` before anything is written. Pseudonymous passenger reference to tools |
| FINMA outsourcing / third-party risk | Payments as a separate institution behind a trust boundary, scoped short-lived agent tokens, idempotency; the processor's record reconciled against the ledger |
| SOC 2 CC6: logical access | Per-agent default-deny tool policy, approval-gated tools; authenticated console users with roles, approver identity from the session, optional segregation of duties |
| PSD2 strong customer authentication | Hosted Checkout: the customer confirms and authenticates on the processor's page. Wallet payments are merchant-initiated under a mandate (the saved card, authenticated at setup, and a per-booking limit); an issuer's authentication request falls back to the hosted page instead of failing or retrying |
| PCI DSS scope reduction | The card number is typed only on the processor's hosted page and vaulted there; the lab stores processor ids, brand, last four and expiry; the model, agents, checkpoints and audit never see card data; payment tokens are single use and stored as hashes |
| ISO 27001:2022 A.8.15: logging | Append-only, tamper-evident audit log readable via `GET /audit` and `GET /audit/verify` |
